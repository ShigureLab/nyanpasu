# Review workflow

The parent owns the working account of the change, cross-scope reconciliation, final verification and publication. Allocate investigation by responsibility; use general/deep to report delivery progress. reviewer.md supplies investigation criteria, scope-review.md supplies repository admission criteria, and review-output.md supplies eligibility and publication protocols. Nyanpasu task control supplies the operation schemas and manages execution, ownership, pinning, waits and frozen results.

## Establish this turn's work

Read and apply review-output.md's live-label eligibility check before review work or any GitHub writes. Read the existing dashboard and repair a missing one through its publication protocol before bulk diff reads, tests, replies or review publication. In read-only mode retain the same evidence locally. A failed dashboard operation may leave an uncertain outcome: inspect before retrying; read-only analysis can continue while publication remains blocked.

Read the PR description, original requirements, current requests and surrounding discussions. For a continuation, use the configured review CLI's `pr view` with `--after <previous fetched_at>`; use a full view when that timestamp is unavailable. Expand each triggering thread and every new human review's body and relevant replies, including APPROVED reviews. A collapsed entry or approval state does not establish that feedback is addressed. Preserve broader human corrections with their rationale, scope and source even when no reply is needed.

Address outstanding explicit requests and replies to your findings. An unchanged head or empty review body does not dispose of requests in inline comments. If an action is outside policy or unavailable, explain the limitation in its original discussion when publication is enabled. A new relevant human request may receive one fitting reaction through github-conversation; check for an existing reaction and do not react to yourself or unchanged automatic updates.

Before reusing coverage or applying silence, compare the pinned inventory with the dashboard source and current requirements with the recorded sources. Verify prior review and publication; a previous task head is only a navigation hint. Resume unfinished work and reassess changed responsibilities or constraints. When inventory and requirements are unchanged and review/publication are complete, an automatic follow-up without new evidence, finding status, decision or outstanding request needs no GitHub write. A policy upgrade alone does not reopen a completed review.

For a substantive round, update the existing dashboard to reviewing with the current source and stage summaries describing this range's actual coverage. Reset stage summaries when the inventory changes even if the head is unchanged; old completion does not establish coverage of a different range. Preserve stable findings and canonical threads, distinguishing resolved, partially resolved, unresolved and superseded issues. For a stacked PR use its direct-base diff, attribute inherited findings to their introducing layer and reuse canonical discussions; approval covers only this PR's reviewed scope.

Call `ci-refresh` at entry. For current failures follow ci-followup.md alongside the code review; a dedicated CI-only follow-up uses that workflow alone. Pending/running CI does not keep the review alive: the observer supplies later failure follow-ups. CI evidence has its own source and does not establish code-review coverage.

## Allocate investigation

Follow scope-review.md to inspect the pinned inventory and submit repository admission decisions before bulk implementation review or child dispatch. Check that the worktree and diff match the pinned head and merge-base. Review coverage must account for the whole admitted scope, using reliable earlier evidence where responsibilities and requirements are unchanged. Earlier correctness findings or task completion alone do not establish necessity coverage; include outstanding production/test necessity scope in an incremental review.

Group admitted responsibilities and identify their questions, evidence needs and owners in `review-plan.json`. For reviews spanning multiple subsystems, delegate cohesive module investigations and cover the remaining work yourself. Small, cohesive changes can stay in the parent. Your global account comes from the contracts, boundaries and reconciled evidence; each investigator traces complete paths for its owned scope. Choose assignments while establishing the scope and questions, then create the selected children once admission is accepted; do not first complete the investigation you intend to delegate.

Assign one primary investigator to each question or experiment. The parent covers its own questions and cross-scope interactions while children investigate theirs; CI runs broad tests in parallel. Reading a shared file for different questions is useful overlap. Independently repeating the same searches or tests needs a specific verification reason. For head-based children, include available parent/CI checks and their revision, commands, results and limitations in the child's prompt or inputs. Preserve independent-design isolation and reconcile returned evidence before deciding that another run is needed.

Create managed children through Nyanpasu task control, choosing the following roles according to the evidence needed:

| Role                 | Purpose and inputs                                                                                                                                                                                                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scoped investigator  | Review a module interaction, trace a correctness question or test a concrete smaller alternative at the pinned head. Use a descriptive `purpose`, `kind: github_reviewer.review` to use its configured execution settings, and self-contained `prompt`/`developer_instructions` with the question, contract sources and evidence that would support or refute it. |
| Test auditor         | Use `purpose: test-audit` for substantial suites or an independent adversarial check. Supply questions about detection power and avoidable maintenance; test-review.md supplies the method. Short checks may stay with the assigned investigator.                                                                                                                 |
| Independent designer | Use `purpose: independent-design` for a material question about minimum responsibilities or decomposition that a fresh requirements-based reference can resolve. An explicit request for independent comparison requires it.                                                                                                                                      |
| CI analyst           | Use `purpose: ci-analysis` and the observed fingerprint under ci-followup.md. It has a separate execution policy and needs no admission scope or `review_files`.                                                                                                                                                                                                  |

For every code-review child, supply accepted changed files in `inputs.review_files`; the service validates them against the root plan and parent's assignment. Give head-based investigators the PR context, target head, question and owned scope. They may read related files for context and return concise conclusions, checked paths, evidence, rejected candidates and gaps even when no findings emerge. Necessity investigation belongs to these assignments and the parent regardless of whether an independent reference runs.

Copy `review_files` from the accepted inventory; context files that are unchanged or outside the assignment do not belong in that list. A successful `create` returns a managed child task ID. A shell background-command ID does not establish that a child exists. If dispatch unexpectedly remains pending, inspect the command/request error and correct it before relying on the assignment; do not spend repeated long `TaskOutput` waits on a dispatch command. Serialize the request to a file and pass that file to the supplied control client to avoid shell quoting and stdin/redirection errors.

Decide `run`, `skip` or `reuse` for an independent reference before reading the implementation when feasible and record the reason, source and requirement sources in the plan. State/lifecycle changes, new abstractions, boundaries and complex algorithms are reasons to consider a reference, not automatic triggers. Mechanical changes or narrow corrections to an already validated design may be skipped with a concrete reason. Reuse requires an identical frozen source tree, requirements and constraints, citing the prior task and artifact hashes; a matching head alone is insufficient. Recheck integration when the target base changes.

An independent-design request also needs `inputs.reason` and `inputs.requirements`, each with `text`, `source` and `provenance` (`explicit`, `base-contract` or `inferred`); optional inputs are `constraints`, `non_goals` and `unknowns`. The service replaces the prompt, exports the pinned merge-base tree into a fresh repository and freezes the input manifest. Supply original observable requirements and compatibility constraints, label inferred or missing requirements, and omit author implementation, new tests and your candidate design. If you already know the implementation, disclose that while preserving the fresh child's isolation. Never feed implementation-derived hints before it freezes its reference. This is input isolation, not an OS/network security boundary.

## Investigate and deliver available conclusions

Creating a child starts it asynchronously. Continue the parent's assigned questions and cross-group interactions while it runs. Audit tests under test-review.md and investigate design necessity alongside correctness. Use design-comparison.md for reference reconciliation or extended deletion/consolidation experiments. Keep small experiments with the responsible investigator; long work may use a scoped child. A child completion or agreement between designs does not resolve the parent's remaining questions.

Deliver supported conclusions for checked scope as they become available; do not hold them until all general-review questions or child work finish. Keep the general stage running while its scope remains incomplete. As soon as general review is ready, save the checked scope, supported correctness and simplification findings, commands/results and remaining questions in `general-review.md`. Publish verified actionable findings and update the dashboard with the delivered scope and conclusion; its general/deep stages describe available conclusions and outstanding investigation. Do this before waiting for children or starting a long deep experiment. General completion does not approve unexamined scope. Do not submit an empty GitHub review merely to announce progress; the dashboard is the status channel.

If necessary evidence and production/test necessity decisions are already reconciled, finish in the same turn. Otherwise retain the completed general result, record the remaining scope as pending/running, and call `await` only after its checkpoint is delivered and useful parent work is complete. End the turn after `await`; the service resumes it with terminal child states and frozen evidence. Do not poll or sleep. Report the delivered result, verified dashboard link and pending scope accurately.

## Reconcile and finish

On resume, repeat the entry checks and compare current head, requirements and constraints with the plan and frozen child inputs. Cancel obsolete children when the PR closes or the range is superseded; retain their evidence at its original identity. Reinvestigate affected conclusions and obtain a fresh reference for changed requirements. Keep still-applicable evidence with its assumptions, and do not rerun or republish unchanged general work.

Inspect returned artifacts and assess the evidence yourself. Use design-comparison.md to reconcile outstanding production/test necessity decisions, with test-review.md for test-specific evidence. A failed child, contaminated reference or essential evidence gap leaves the assigned work incomplete until recovered; it does not erase the delivered general result. Deep completion requires reconciled necessity evidence for applicable scope, including justified retention decisions; zero simplification findings is valid. Skip deep only when there is no applicable work, with a concrete reason.

Before final publication reread requirements and relevant discussions, refresh CI and require `review-verify` to match the range actually reviewed. It verifies eligibility and range, not unchanged requirements. A changed range requires a new run: report it and do not publish this run's conclusions or relabel its evidence. Follow review-output.md for the actual review decision, dashboard data, canonical comments, disclosure, draft recovery and confirmed publication. Only the parent publishes. Finish with the actual outcome, verified links, or the concrete remaining evidence/publication gap.
